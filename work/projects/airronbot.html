What this shows

This is not a chatbot I subscribed to. It is a system I designed so tools that were never built to work together can pass work to each other, with clear rules about what each one is allowed to do.

The front door is Airronbot, a Discord bot I specified and host on Replit. When someone in one of my servers asks it a question, the bot does not invent an answer. It carries that question to a Grok Bot agent I set up. The agent can use my connected accounts if the question needs them, and the reply comes back into Discord without pinging anyone or lighting up phones.

How a question travels

This is the path of a single question. If you only look at one thing on this page, look at this.

  1. Someone asks in DiscordA server member addresses Airronbot with a question.
  2. The bot decides whether to forward itOnly addressed server messages are sent on. Unrelated chat, direct messages, and other bots are ignored. The message is given an ID so it will not be handled twice.
  3. The question is sent to the relayAirronbot posts the message over HTTPS to a webhook routine I configured, and expects a receipt within ten seconds. Redirects are rejected.
  4. The agent writes the answerA Grok Bot agent I configured drafts the reply under rules I set: no @mentions, no personal details, silent delivery.
  5. The answer comes back, signedThe agent posts the reply to the bot’s callback with a shared secret. That secret is different from the outgoing webhook key, and it is checked with a timing-safe comparison.
  6. The bot posts a quiet replyIf the secret is valid and the message is not a duplicate, Airronbot posts the answer in the channel without a notification. It can also speak the answer in a voice channel.

If the relay is down, the bot posts a fixed notice. It never falls back to another AI on its own. Slash commands, birthdays, welcomes, and the health page keep working even when the agent is offline.

The full system

The same agent is also connected to my email, calendar, files, code, and website. I chose those connections and the trust level for each: some may only be read, and sending a message or changing an account needs my approval first.

Solid arrows are the main path of a question and a deploy. Dashed arrows are the signed reply back to the bot, and the weekly analytics report back to the agent.

1. Project overview

Airronbot began as a Discord bot for my own community and became the front door to a small, connected AI system. A message addressed to the bot travels over an authenticated webhook to a Grok Bot agent I configured. The agent drafts the answer under rules I set, sends it back through a secured callback, and the bot posts it silently. It can also speak the answer in a voice channel.

Around that bridge I connected the same agent network to Gmail, Google Calendar, Google Drive, Replit, GitHub, and my website analytics, with scheduled routines for recurring work. The engineering is in the system design: what each service is trusted to read or do, how messages move, and where a human has to approve an action.

2. Original motivation

I began using ChatGPT during graduate school at Full Sail to help write scripts, and used that AI-assisted workflow to build a Discord bot that could run continuously for my community. I have not found the original school-era source to attach here; that starting point is from my own account. As AI agents became able to use real tools, I wanted the bot to stop being a closed box of commands and become a connection point: a place where people could ask questions and where my assistant could act across the services I use every day.

Coming from game design, I treated it like a systems problem: independent pieces with their own rules, connected by clear interfaces, with behavior that can be inspected and tuned.

3. Technical architecture

Two separate programs share the work. Airronbot owns the Discord connection: it receives events, filters them, talks to Discord’s API, runs slash commands, and can join voice. The Grok Bot agent owns reasoning and tools: it reads the question, may look at email or files if needed, and writes the reply. They trust each other only through credentials I configured. The outgoing webhook uses one key; incoming replies use a different shared secret. Those two keys cannot be swapped.

I also set up two peer agents, Game Bot and Bartenbot, so work can be split. Deploys to my website go through git on a shared Linux computer, then GitHub Pages. Visitor counts from GoatCounter feed a weekly rundown.

6. Technical challenges and solutions

  1. Two-way trust between separate servicesThe outgoing webhook uses its own bearer key. Incoming callbacks need a different shared secret, compared by SHA-256 with a timing-safe check. The two keys are never interchangeable.
  2. Duplicate repliesEach message is claimed before forwarding. Callbacks are deduplicated by the original message ID for an hour, and Discord’s nonce covers overlapping restarts.
  3. Preview and production fighting over one botThe preview build never opens a Discord connection or joins voice, so only the published bot answers.
  4. Social rules as code, not just promptsA shared send wrapper forces notification suppression and blocks all mentions on every outgoing message, including @everyone.
  5. Voice without a paid speech APILocal eSpeak-NG WebAssembly runs in a short-lived worker with a 60-second timeout, a per-server queue capped at five, and staged failure codes on the dashboard.
  6. Safe agent actions inside DiscordAuthenticated endpoints let the agent create a channel, scan or repost images, list members by join date, or set the avatar, each with validation and permission checks. Image reposts have a host allowlist, a size cap, a dry-run mode, and rate limiting.
  7. Not leaking secrets in errorsError responses and logs omit webhook URLs, tokens, message bodies, and raw Discord errors.

8. Results and limitations

The bot is published, connected to three Discord servers, and answers addressed messages through the Grok Bot relay. The same agent network handles email, calendar, Drive files, site deploys, game builds, and weekly analytics, with outgoing messages held for my approval.

  • Deduplication and the voice queue live in memory; a restart clears them.
  • Birthdays are stored in a local JSON file; the birthday and welcome channels are not configured in production right now.
  • If the Grok Bot platform hits a usage limit or an outage, answers stop and the bot shows a fixed notice.
  • A failed webhook is not automatically retried.
  • No performance or usage metrics are recorded, so none are claimed.
  • The bot source is in a private Replit workspace and is not yet on GitHub.
